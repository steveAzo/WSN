Part 1

The paper in one minute

Read this five times. If you can say it in your own words, you understand the paper.

  1. The problem. A water-quality sensor in a river measures temperature, conductivity, oxygen and pH every 10–15 minutes and sends each reading over a cellular or long-range radio. Every transmission costs a fixed chunk of battery energy, so sending everything drains the battery in months.
  2. The known idea. The sensor and the server can both run the same "guessing" model. The sensor only transmits when the server's guess would be wrong by more than an agreed tolerance. That is called a dual prediction scheme. The server's view is then never wrong by more than the tolerance.
  3. Our question. Papers usually test this on one convenient dataset and assume a smarter guess means fewer transmissions. We asked: when does a smart guess actually beat the simplest one ("the value hasn't changed")? We tested on 14 real water-quality records: 13 US rivers and one real sensor deployment in Kosovo.
  4. What we found. A smart predictor helps only at moderate tolerances, and only on rivers with a strong day–night rhythm. A simple measure of that rhythm predicts the saving very well. On the noisy Kosovo sensor, the simplest scheme is best. Separately, sending all parameters together whenever one must be sent saves another 31–44%, on every site. A competing 2026 method gives up the error guarantee and has 8–17 times larger worst errors.
  5. What we built. A predictor called RLS-D that does nearly as well as the best choice on every site without having to choose. An event alarm on the sensor so real pollution events are not missed. Two ways to handle lost messages. And a battery model from real radio measurements: 1.1–3.5 times longer battery life.
Part 2

The vocabulary

Grouped by topic. For each, read the plain definition, then the example. Cover the definition and say it out loud.

A. The sensor and the radio

Node (sensor node)
The box in the river: sensors, a small computer (microcontroller), a battery, maybe a solar panel, and a radio.Example: the Libelium Waspmote nodes at Weija and in Kosovo.
Sampling cycle, cadence, step (Δt)
How often the node measures. Our data: every 10, 15 or 30 minutes. One "step" is one measurement time.15-minute cadence = 96 steps per day.
Report
One transmission from node to server. It can carry one parameter or all of them.
LPWAN
Low-Power Wide-Area Network: radios designed for small messages over long distances on little power. We use two kinds: NB-IoT and LoRaWAN.
NB-IoT
Narrowband IoT: a cellular (mobile-network) technology for sensors, run by phone operators like MTN. Each report costs about 0.1–1.3 joules with good settings, up to ~4 J with default settings.
RAI (Release Assistance Indication)
An NB-IoT setting where the device tells the network "I'm done, release me now", so it doesn't stay awake waiting. Much cheaper per report.
PSM (Power Saving Mode)
NB-IoT deep sleep between reports. Uses about 10 microwatts.
LoRaWAN, spreading factor (SF7, SF12)
A long-range radio you can run yourself with your own gateway. The spreading factor trades range for speed: SF12 reaches farther but each message takes longer on air, so it costs more energy (~0.7–0.9 J) than SF7 (~0.2 J).
Confirmed uplink, ACK
The server sends an acknowledgement ("got it"). If the node gets no ACK, it knows the message was lost and can retry.
Fixed cost per report
The key fact behind the whole paper: on these radios most of the energy is spent setting up the connection, not on the data. Sending 4 numbers costs almost the same as sending 1.That is why "send all parameters together" is almost free.
Battery life / lifetime
Battery energy divided by energy used per day. Our battery: 6,600 mAh, the same as the Weija node.

B. The reporting schemes

Tolerance δ ("delta")
The largest error we accept at the server. At our headline level L2: temperature 0.2 °C, dissolved oxygen 2 % saturation, pH 0.1, conductivity 2 % of its typical value.
Levels L0–L4
Five tolerance settings from very strict (L0, near sensor precision) to loose (L4). L2 is the middle.Temperature: L0 0.05, L1 0.1, L2 0.2, L3 0.5, L4 1.0 °C.
Reconstruction
The server's version of the readings: real values when reported, guesses when not.
Error-bounded (bounded)
The reconstruction is never more than δ from the truth. This is a guarantee, not an average.
Dual prediction scheme (DPS)
Node and server run the same predictor on the same information. Both make the same guess. The node sends only when its true reading differs from the guess by more than δ. Because both sides compute the same thing, the server knows the error is at most δ when nothing arrives.
Send-on-delta (SOD)
The simplest DPS. The guess is "same as the last reported value". Send only when the reading has moved more than δ from it.Worked example in Part 4, Section III.
Separate, bundled, report-level
Three ways of counting reports. Separate: each parameter that exceeds δ is its own message (how the Kosovo nodes worked). Bundled: parameters that exceed at the same moment share one message. Report-level: if any parameter must be sent, send all of them.
Free-riding
In report-level mode, the parameters that did not need sending "ride for free" in the report. They get refreshed, which delays their own next transmission.
Periodic reporting
Send every X minutes regardless. The server holds the last value in between ("zero-order hold"). What most deployments do, including Weija (every 30–60 min).
Batching
Collect samples and send them together every X minutes. Exact data, but late.
ADAPTIVEML
A 2026 method (Kangethe et al.) that sends when the error exceeds α times the recent variability of the signal. Its tolerance grows when the water changes quickly, so it is not bounded. Our main competitor.

C. The predictors

Predictor
The rule that guesses the next value from past values. SOD's predictor is "last value".
LMS
Least Mean Squares: a simple self-adjusting filter (Santini & Römer 2006). With the paper's settings it sends 92–100% of samples on our data, so it fails.
DBP
Derivative-Based Prediction (Raza et al. 2015): estimate the slope from recent readings and extend it. Very cheap.
Ridge regression
A linear model that predicts the next value from the last 24 values, with a penalty that keeps the weights small. ADAPTIVEML's predictor.
RLS, forgetting factor γ
Recursive Least Squares: like Ridge, but it keeps updating its weights as reports arrive. γ controls how fast it forgets old data. γ = 0.98 (paper default) forgets in about 50 steps, too fast and unstable on our data. γ = 0.999 forgets in about 1,000 steps: that's RLS-T (T for tuned).
RLS-D (ours)
RLS that predicts changes instead of levels, plus two fixes: damping and history repair. Explained with numbers in Part 4, Section V.
RIDGE-D
RLS-D with frozen weights. Safer when messages can be lost silently.
SWITCH
A method that switches between SOD and RLS-T while running. It did not pay (a negative result).

D. Data and statistics

USGS
U.S. Geological Survey. Publishes high-quality, checked river data. We used 13 rivers, 2023, "approved" values only.
InWaterSense
A real low-cost deployment on the Sitnica river in Kosovo (2015). Noisy, fouling-prone. Our "real-world" case.
Diel, diel variance share
Diel = day–night (24-hour) cycle. Rivers warm by day and cool at night; plants make oxygen by day. The diel share is the fraction of a day's ups and downs explained by the time of day alone. 1 = perfectly regular daily rhythm; 0 = no rhythm.Our rivers: site averages 0.12–0.56. Kosovo node: about 0.02.
Persistence
Another name for "last value" as a forecast.
Skill
How much better a model forecasts than persistence: 1 − (model's squared error ÷ persistence's squared error). 0 = no better. 0.5 = errors halved. Negative = worse than persistence.
AR, VAR
Autoregression: forecast a parameter from its own past. Vector autoregression: from the past of all parameters together.
Out-of-sample
Tested on data the model never saw while being fitted. The honest way to measure prediction.
Training / test split (20 / 80)
First 20% of each record (by time) for learning; the remaining 80% for scoring. Like a node installed with a few weeks of history.
Tuning sites / test sites
We split the 13 rivers in advance: 7 for choosing settings, 6 kept unseen (plus Kosovo). Choices made on tuning sites are then checked on test sites. This prevents fooling ourselves.
Median
The middle value when sorted. Less affected by one extreme site than the average.
Spearman ρ ("rho")
Does a higher X go with a higher Y, in rank order? From −1 to +1. ρ = 0.84 means sites ranked by diel share come out in almost the same order as sites ranked by saving.
p-value
How likely a pattern this strong would be by pure chance if there were no real relationship. p = 0.0002 means about 2 in 10,000. Below 0.05 is usually called significant.
Wilcoxon signed-rank test
A test for paired comparisons: on the same 13 rivers, is method A consistently cheaper than method B?
Leave-one-out
Recompute the result 13 times, each time leaving one site out. If the result never collapses, no single site is driving it.
Max error, MAE, RMSE
Worst error ever; average error; root-mean-square error (penalises big errors more). Our guarantee is about the max error.

E. Events and lost messages

Event
A real, sustained change worth knowing about: a storm flush, a pollution pulse, an oxygen crash.
Glitch
A short spike that quickly returns to normal: usually a sensor hiccup.
Check B / reference events
Our offline rule that labels events in the data (more than 5× the normal noise level for at least 1 hour). Used to score methods. Not "ground truth": a statistical label.
Injected events
Fake steps and ramps we add to real data at known times, so we know exactly when an event started. This is the ground truth for testing the alarm.
σ ("sigma")
The normal noise level of a series. A "5σ event" is five times bigger than normal wiggles.
CUSUM detector
Cumulative Sum (Page 1954). Keep a running total of how much each reading is "more surprising than usual". Small surprises fade away; a sustained surprise piles up. Alarm when the total passes a threshold H.
False alarm
An alarm when no labelled event is present. Our target: at most about 2 per parameter per month.
Packet loss
A report that never arrives. Real NB-IoT networks lose 0.5–1%.
Sequence number, heartbeat
Each report carries a counter, so the server notices a gap. A heartbeat is a full report sent every 6 or 24 hours, which resets both sides.
Bounded or flagged
Our guarantee under loss: every value the server shows is either within δ, or marked "unverified".
Equal-accuracy comparison
Comparing schemes that deliver the same worst error, or the same battery life, so we don't compare a careful scheme with a sloppy one.

Try these, in order

  1. Clean river, δ = 0.2. The predictor sends far fewer reports. It "rides" the daily curve while SOD makes a staircase. Notice that both keep the error within δ: that's the guarantee.
  2. Now raise the noise to 0.15. The predictor gets worse than SOD. Noise makes the trend look random, and every wrong trend guess costs a report. This is the Kosovo case.
  3. Set noise to 0.08 and move δ from 0.05 to 1.0. At 0.05, SOD wins (no predictor beats noise). Around 0.2–0.5 the predictor wins. At 1.0 both send almost nothing. That is the sweet spot from Table IV of the paper.
  4. Set the swing to 0.3. With a weak day–night cycle, there is little to predict, so SOD is as good or better. That's why diel share predicts the saving.

Abstract

A summary of everything in about 250 words. Problem, approach, four findings, what we built, energy result. Reviewers often decide from the abstract alone whether to read on.

Remember

"We asked when prediction pays, on 14 real water-quality records, and found it depends on the river's day–night rhythm and on the tolerance."

I. Introduction

Explains why the problem matters (fixed energy per report on NB-IoT and LoRaWAN), what is already known (dual prediction), the two gaps (evaluation on one dataset; per-parameter decisions that ignore the per-report cost), the four research questions RQ1–RQ4, and the contributions.

The four research questions are the skeleton of the whole paper:

  • RQ1: when does prediction beat send-on-delta, and what property of a site explains it?
  • RQ2: how much does deciding per report (instead of per parameter) save, and why?
  • RQ3: can we keep the error guarantee, catch events, and survive lost messages, while matching adaptive methods?
  • RQ4: what does it buy in battery life on real radios, and when does it matter?

Note the honest motivation: the Prof's own Weija paper chose 30–60-minute reporting "to overcome communication delays and energy consumption". Our paper offers a principled alternative with a guarantee.

II. Related Work

What others did, and the gap. Know these five names:

  • Santini & Römer (2006): original dual prediction with LMS; the rule that both sides feed the guess when nothing is sent. Also first suggested a joint (block) decision but never built it.
  • Raza et al. (2015): DBP; in a real tunnel, 99% suppression gave only 3–7× battery life because fixed network costs dominate.
  • Ghosh et al. (2022): multi-sensor hub that batches readings (adds delay) and uses fixed alarm limits.
  • Kangethe et al. (2026), ADAPTIVEML: our main competitor; adaptive threshold, not bounded.
  • Michelinakis et al. (2021), Casals et al. (2017): measured energy of NB-IoT and LoRaWAN, which our battery model uses.

Table I is the gap table: each ✓ is a capability. Our column is the only one with all ✓. Be ready to say what is not new: the report-level idea itself (Santini proposed it, Ghosh batched). What's new is measuring it on many real sites under bounded errors and LPWAN costs.

IV. Data and Predictability Measures

  • Why USGS? High-quality, checked data from many different rivers, so we can ask "on which kinds of river does prediction pay?". The sites were picked by a rule written before looking at results (no cherry-picking). One selected site had no data that year and was dropped, not replaced.
  • Why InWaterSense? A real low-cost deployment with the same hardware family as Weija: noisy, with fouling. It represents what deployed nodes really see.
  • Table II: every dataset, its type, whether it was a tuning or test site, its cadence and length.
  • Check A: how predictable each series is, honestly (out-of-sample).
  • Diel share: the day–night rhythm measure. Cheap, model-free.
  • Check B: the offline event labels.

Detail you may be asked: the Kosovo data looked 18% missing in the published grouped file, but when we rebuilt the original messages only 3–6 cycles were really incomplete. The missing values were a file-assembly artefact.

V. Methods and Evaluation Protocol

The baselines (the methods we compare against), our method RLS-D, the event detector, the loss protocols, and the rules of the evaluation.

RLS-D in plain words

Between reports, the predictor runs "blind" on its own guesses, sometimes for hours. Two things go wrong with ordinary learned predictors:

  1. Drift. A trend guessed at 06:00 keeps being extended for hours, even though the river has stopped warming. Fix: damping. The predicted change is multiplied by φk, where φ = 0.97 and k is the number of steps since the last report. At 15-minute steps: after 1 hour the trend is kept at ×0.89, after 6 hours ×0.48, after 12 hours ×0.23. So a long silence fades into "hold the last value", which is SOD.
  2. The fake jump. Suppose the last report was 25.0 at 06:00, the predictor guessed flat, and at 07:15 a report says 25.5. The history now shows 25.0, 25.0, 25.0, 25.0, 25.0, then 25.5: a jump of 0.5 in one step. The predictor thinks the river is warming fast and extrapolates. Fix: history repair. Both sides replace the blind guesses with a straight line: 25.0, 25.1, 25.2, 25.3, 25.4, 25.5. Now the slope is a realistic 0.1 per step.

Both fixes use only information the server also has, so node and server stay identical. The damping value φ = 0.97 was chosen on the 7 tuning sites by a written rule, then tested on the others.

The CUSUM detector, with numbers

Each step, the node computes how surprising the reading is (z, in units of normal noise). It adds z − k to a running total S (never below 0), with k = 3. Alarm when S passes H = 8.

z values 1, 4, 5, 4.5, 5, 5 give S = 0, 1, 3, 4.5, 6.5, 8.5. The last one passes 8 → alarm. One big spike alone can't reach 8 (each step adds at most c − k = 3), so short glitches don't trigger it, but a sustained shift does.

The evaluation rules (why the results are trustworthy)

  • Train on the first 20%, score on the last 80%.
  • Tuning sites (7) and test sites (6 + Kosovo) were fixed before any result was seen.
  • Every bounded run is checked automatically: the error never exceeded δ, in all 2,016 runs.
  • 83 automated tests check the simulator (for example, that the server's view can be rebuilt from the reports alone).

The energy model, equation (3)

Daily energy = sleeping + measuring + reporting. Only the reporting part depends on our scheme. Battery life = battery energy ÷ daily energy. The numbers come from published measurements of real modules (Michelinakis, Casals). The model reproduces 20 of 24 battery lifetimes from Michelinakis's table; the other 4 contradict that paper's own equation.

VII. Discussion

  • Practical guidance: six rules for engineers. Always decide per report. Use SOD on noisy nodes. Use RLS-D where the day–night cycle is strong. Protect events with a detector, not a tighter δ. Match the loss protocol to the radio. Compare at equal accuracy.
  • Limitations: one year of US data plus one deployment; the Weija paragraph; tolerances not regulatory; events labelled by a rule; energy from published measurements, not our own hardware.
  • Conclusion: prediction pays only sometimes, and we can tell when.
The Weija paragraph

We wrote down a prediction before testing Weija: "diel share says 30% saving". The result was −16% (prediction cost reports). The sensor's temperature spiked 2–7 °C at midday, which suggests a sun-heated sensor. The paragraph is marked for the Prof: keep or drop. If he asks, the honest answer is that the data had problems (pre-processed files with hidden interpolation, sensors failing in January), but the failed prediction also teaches us that diel share alone is not enough.

Part 5

The results, one by one

For each result: what we found, the number, why it happens, and where it is in the PDF.

RQ1a. Most clean rivers are predictable; the Kosovo node is not

One hour ahead, prediction beat persistence by more than 10% for temperature on 10/13 rivers, pH 11/13, oxygen 8/13, but conductivity only 3/13. On Kosovo: none. Why: temperature, oxygen and pH follow sun and plants; conductivity changes with rain and upstream flow, which a sensor can't see coming. Where: Section VI-A, Fig. 1.

RQ1b. The day–night rhythm explains predictability

Diel share vs forecast skill: ρ = 0.66 across 52 site–parameter pairs. Kosovo's diel share is only 0.01–0.04. Why: a regular daily rhythm is exactly what can be forecast.

RQ1c. The costliest months are the most predictable

For temperature, ρ = +0.78 between a month's reporting cost and its predictability. Summer has big daily swings, which make SOD expensive, but those swings are regular, so prediction helps most when it's needed most. In calm winter months, prediction can be worse than SOD.

Why: at L0, the tolerance is smaller than sensor noise, so no prediction helps. At L4, both send almost nothing, so there is nothing left to save. In between, prediction pays. You saw this in the toy.

RQ1e. Diel share predicts the saving: the central result (Fig. 2)

ρ = 0.84 at L2 over 14 datasets, p = 0.0002. Without Kosovo: 0.80. Leaving out any one site: never below 0.75. Sites with low diel share save 6–15% (one exception at 30%); sites above 0.40 save 26–43%. Why it matters: an engineer can compute diel share from a few weeks of data and know whether a smart predictor is worth it, before deploying. Caveat: Weija showed it's not sufficient on its own.

RQ2. Report-level decisions save 31–44% (Table V)

At strict tolerances most of the saving comes from bundling (several parameters exceed at the same time). At loose tolerances most comes from free-riding (refreshing the others delays their next report). Free-riding helped in 253 of 260 cases. It works on Kosovo too (33–43%), even though prediction doesn't. The practical message: do this always; it costs nothing.

RQ3a. Keeping the guarantee costs nothing in reports (Fig. 3)

We paired each ADAPTIVEML run with our bounded RLS-T run that sent about the same number of reports. ADAPTIVEML's worst error was 8–17× larger in every single case (11.8× at its default setting). Why: its threshold widens when the water changes fast, which is exactly when errors matter. Periodic reporting at the same rate: worst errors 2.5–24× larger. Batching: exact, but 15–120 minutes late.

RQ3b. RLS-D works without choosing (Table VI)

The best predictor differs by site: SOD on noisy sites, RLS-T on rhythmic rivers. You only know which in hindsight. RLS-D comes within a median of 0.5% of that hindsight-best at L1–L3 (2.4% at L4), on the unseen test rivers. SOD alone is 22–36% worse there. On Kosovo, RLS-D costs 3–13% more than SOD: an honest limit.

The three negative results (and why they're in the paper)

  1. Choosing the predictor at installation from early data picked wrong 29–50% of the time. The early data is winter, when SOD is enough; summer is where prediction pays.
  2. Switching while running was stable but didn't save reports.
  3. Halving δ during events cost more reports than it gained.

Good journals respect negative results with a diagnosis. They show we didn't hide what failed, and they save other researchers time.

RQ3c. Events (Fig. 4, Table VII)

A bounded scheme doesn't guarantee that events are seen: at L4 only 0.63 of real events are reported while happening, because events smaller than δ never trigger a report. The CUSUM detector catches 70% of injected 5σ steps (85% of 8σ), but only 5–24% of slow ramps. About half its "false" alarms actually fall near real events (6× more than chance), so the true false-alarm rate is about one per parameter per month.

The headline comparison: running at L4 with the sensitive detector catches more injected events than tightening to L3 (0.97 vs 0.87) using only 40% of the reports. Limit: slow, gradual real events are still hard.

RQ3d. Lost messages (Table VIII, Fig. 5)

With acknowledgements, retries keep both sides in step; the cost is about the loss rate. Without acknowledgements, sequence numbers plus heartbeats give "bounded or flagged": 0 unflagged violations in 1,120 runs. SOD heals itself with any report, so it's the robust choice there.

RQ4. Energy (Tables IX, Figs. 6–7)

  • Battery life 1.1–3.5× longer than reporting every cycle, depending on radio and sensing time. NB-IoT with RAI, 5 s sensing: 2.56 → 4.62 years (1.72×).
  • RLS-D over SOD: only about 5% more battery life on efficient radios (17% with default NB-IoT settings), because after suppression the sensing itself dominates.
  • The strongest claim, equal accuracy: at about the same battery life as hourly reporting, our worst error is 7.8× smaller, and events arrive immediately. At the same worst error as 30-minute reporting, we last 53% longer.
  • Honest framing: a 2 W solar panel gives at least 33× the energy needed, so for solar nodes energy isn't the argument. The value there is smaller hardware, cheaper data plans and radio duty-cycle limits. That framing is one of the decisions for the Prof.

Part 7

Questions he may ask

Try answering each one yourself before opening it.

What is new here? Isn't this just send-on-delta?

Send-on-delta is our baseline, and we show it is actually the best choice on noisy nodes. What's new: (1) the first study across many real water-quality sites of when prediction beats it, with a simple predictor of the saving (diel share); (2) measuring how much report-level decisions save and why; (3) showing that keeping the error guarantee costs nothing compared with ADAPTIVEML; (4) RLS-D, plus a detector and loss protocols, evaluated together with real radio energy.

Why simulate instead of deploying?

Trace-driven simulation replays real recorded data, so the signals are real; only the transmission decisions are simulated. It lets us test 14 sites and thousands of settings fairly, which a deployment could never do. The energy comes from published measurements of real modules. Hardware validation is listed as future work.

Why US data instead of Ghana data?

We needed many sites with long, quality-checked records to answer "on which kinds of river does it pay". USGS publishes exactly that. Kosovo gives the real low-cost deployment. We screened Weija too, but after cleaning only about nine weeks of two parameters were usable, and the sensors showed midday spikes we need his help to interpret.

Why not deep learning (LSTM)?

Two reasons. The node must run the predictor itself, on a small microcontroller, every 15 minutes. And our results show the limit is the signal, not the model: on noisy data even the best forecast can't beat "last value". A bigger model doesn't fix noise.

How do you know the error bound really holds?

It holds by construction: a value is only skipped if the guess was within δ. We also check it automatically in every run (0 violations in all 2,016 baseline runs), and unit tests rebuild the server's view from the reports alone.

Why did RLS-T need a different forgetting factor from the paper?

With γ = 0.98 the model forgets in about 50 samples while estimating 24 weights; on 15-minute river data it became unstable and reported most samples. We report both the paper default and our tuned 0.999, so nobody can say we weakened the competitor.

Why are the tolerances what they are?

They are a sweep from sensor precision (L0) to coarse monitoring (L4), and we report results per level. We'd like his guidance or a regulatory reference (Ghana EPA, WHO) for the values a water utility would accept.

Does energy matter if the nodes are solar-powered?

For a 2 W panel, not much: there is at least 33× more energy than needed. The value of fewer reports then is smaller and cheaper hardware, lower data costs, and radio duty-cycle limits. For battery-only nodes (enclosed, submerged, in pipes or manholes) the 1.1–3.5× lifetime gain applies directly. We propose to frame RQ4 that way.

Part 9

Test yourself

Answer out loud first, then open.

1. Why is sending all parameters together almost free?

On NB-IoT and LoRaWAN most of the energy per report is the fixed cost of connecting, not the data. Adding three more numbers barely changes the cost.

2. Why does prediction not help at L0?

The tolerance is smaller than the sensor noise. The noise itself triggers reports, and no predictor can forecast random noise.

3. Why does prediction help little at L4?

Both schemes send very few reports at such a loose tolerance, so there is little left to save.

4. What does ρ = 0.84 mean in plain words?

If you rank the sites by their day–night rhythm and by how much prediction saved, the two rankings are almost the same.

5. What is free-riding?

When one parameter must be sent, the others are sent too. That refreshes the server's copy of them, which delays their own next report.

6. Why is ADAPTIVEML's worst error so large?

Its threshold is α times the recent variability of the signal. When the water changes fast, variability is high, so the threshold widens exactly when accurate data matters most.

7. What two problems does RLS-D fix?

Drift during long silences (fixed by damping, which fades the trend towards "hold") and the fake jump when a report arrives after a silence (fixed by history repair, which replaces the guesses with a straight line).

8. Why can't the bounded scheme alone protect events?

An event smaller than δ never makes the error exceed δ, so it never triggers a report. The node-side detector looks for sustained surprises instead.

9. What does "bounded or flagged" mean?

Under message loss, every value the server shows is either within δ or marked as unverified. There is never a wrong value presented as correct.

10. Why split tuning and test sites?

If you choose settings and then test on the same sites, the result looks better than it is. Choosing on 7 sites and checking on 6 unseen ones shows the method works on new rivers.

11. What did Weija teach us?

A strong day–night rhythm is not enough on its own. If the daily signal is a sharp spike instead of a smooth curve, a predictor that only looks at recent values gets no warning, and SOD wins.

12. What is the strongest energy claim and why?

At about the same battery life as hourly reporting, our worst error is 7.8× smaller, and events arrive immediately. It compares at equal battery life, so it isn't comparing a careful scheme with a sloppy one.
